# תכנון החתונה שלי — Wedding Planner

אפליקציית React + Vite (עברית, RTL) לניהול מוזמנים, הושבה, ספקים ותקציב.
עובדת גם לחלוטין מקומית (localStorage) וגם מול **CockroachDB** עם ריבוי
חתונות ושיתוף בין משתמשים.

```bash
npm install
cp .env.example .env    # ומלאו DATABASE_URL
npm run db:migrate      # פעם אחת, ואחרי כל שינוי סכימה
npm run dev             # Vite על 5173 + API על 3001
npm run build
npm run lint
```

## ארכיטקטורה

```
דפדפן (React) ──fetch /api/*──► שרת Node/Express ──pg──► CockroachDB
                  עוגיית httpOnly       SET LOCAL ROLE app_user + RLS
```

הדפדפן לעולם אינו מדבר עם המסד ישירות, ואין בו שום סוד.
ל-CockroachDB אין שירות הזדהות ואין API אינטרנטי — ולכן השרת הוא חובה,
והוא גם המקום היחיד שמחזיק את `DATABASE_URL`.

| קובץ | תפקיד |
|---|---|
| [db/001_init.sql](db/001_init.sql) | כל הסכימה וכל מדיניות ה-RLS |
| [server/db.js](server/db.js) | `withUser` (כפוף ל-RLS) מול `withAdmin` (עוקף) |
| [server/auth.js](server/auth.js) | scrypt, סשנים, עוגיות |
| [server/api.js](server/api.js) | נתיבי ה-API |
| [src/lib/cloudStore.js](src/lib/cloudStore.js) | הלקוח מול ה-API |

## אבטחה — חובה לקרוא

האפליקציה רב-דיירית: לכל משתמש יש חתונה משלו, וניתן לשתף חתונה עם אחרים
בתפקיד `owner` / `editor` / `viewer`. **הגבול בין דיירים נאכף במסד הנתונים**
(RLS), לא ב-UI ואפילו לא בשרת. גם באג בקוד השרת לא יחשוף נתונים של חתונה
אחרת, כי כל שאילתה רצה תחת `SET LOCAL ROLE app_user`.

### הרצת המיגרציה (חובה)

```bash
npm run db:migrate
```

הסקריפט מריץ את [db/001_init.sql](db/001_init.sql) הצהרה-אחר-הצהרה (CockroachDB
לא מריץ כמה שינויי סכימה בטרנזקציה אחת). הקובץ אידמפוטנטי — אפשר
להריץ שוב בבטחה.

המפתח הראשי בארבע טבלאות הנתונים הוא `(wedding_id, id)` ולא `id` לבדו,
כי מזהי רשומות נוצרים בצד הלקוח כ-`max(id)+1` ולכן שתי חתונות יכילו
שתיהן מוזמן `id = 1`.

### שלוש מלכודות של CockroachDB שהקוד מטפל בהן

1. **אין משתני סשן מותאמים.** אין `SET app.user_id`. לפי התיעוד הרשמי
   של Cockroach, זהות הדייר עוברת בתוך `application_name`. השרת קובע
   `wp:<uuid>` בכל טרנזקציה, ו-`app.current_user_id()` שולף משם.
2. **אין בלוקי `DO $$ … $$`.** כל הלולאות במיגרציה פרושות ידנית.
3. **ביטוי מדיניות לא יכול להכיל תת-שאילתה.** לכן כל הלוגיקה עוברת
   דרך פונקציות `SECURITY DEFINER`.

> ⚠ מגבלה מתועדת של CockroachDB: מפתחות זרים, אילוצי UNIQUE ו-`TRUNCATE`
> עוקפים RLS. אין להשתמש בהם כגבול אבטחה.

### סודות

⚠ **`DATABASE_URL` לעולם לא עם קידומת `VITE_`.** כל משתנה שמתחיל ב-`VITE_`
נצרב לתוך ה-bundle ונחשף לכל מי שפותח את האתר. המשתנה היחיד שנחשף
לדפדפן הוא `VITE_API_URL`, והוא לא סוד.

### כותרות אבטחה בפריסה

[public/_headers](public/_headers) נארז אוטומטית ל-`dist/` ונתמך ב-Netlify
ו-Cloudflare Pages. הוא מגדיר CSP (`default-src 'self'`, `frame-ancestors
'none'`, `connect-src 'self'` בלבד), HSTS, `nosniff`, `Referrer-Policy:
no-referrer` ו-`Permissions-Policy` שחוסם מצלמה/מיקרופון/מיקום.

- `style-src` כולל `'unsafe-inline'` בכוונה — React מציב `style` inline והפונטים
  נטענים מ-Google Fonts.
- `connect-src 'self'` מספיק כי ה-API יושב על אותו origin. אם תפריסו את
  השרת על דומיין נפרד, הוסיפו אותו שם — וגם שנו את העוגייה
  מ-`SameSite=Strict` ל-`None; Secure`, אחרת הדפדפן לא ישלח אותה.
- ב-Vercel/שרת אחר — העתיקו את אותן כותרות ל-`vercel.json` / קונפיג ה-nginx.

### גיבויים מוצפנים

כפתור **גיבוי** מציע הצפנה בסיסמה לפני ההורדה: PBKDF2-SHA256 (250,000 סבבים,
salt אקראי) → AES-GCM עם IV אקראי. ה-salt וה-IV נשמרים לצד ה-ciphertext.
**אין שחזור סיסמה — סיסמה שאבדה = קובץ שאבד.** קובץ לא מוצפן מכיל את השמות
והטלפונים של כל המוזמנים בטקסט גלוי.

### התנהגות נוספת

- **התנתקות אוטומטית** לאחר 30 דקות של חוסר פעילות (`IDLE_LOGOUT_MINUTES`).
- **ניקוי מלא ביציאה** — כל מפתחות `wp:v1:*` נמחקים מה-localStorage.
- **עוגיית httpOnly** — טוקן הסשן אינו נגיש ל-JavaScript בכלל, ולכן XSS
  לא יכול לגנוב אותו. במסד נשמר רק SHA-256 שלו.
- **namespacing** — במצב ענן המפתחות הם `wp:v1:<userId>:<weddingId>:<key>`,
  כך ששני משתמשים על אותו מחשב לא רואים את המטמון זה של זה. במצב מקומי בלבד
  (ללא `VITE_API_URL`) נשמרת התחילית הישנה `wp:v1:<key>`.
- **שדרוג ממצב מקומי** — משתמש שעבד ללא שרת ואז התחבר יישאל במפורש האם
  לייבא את הנתונים הישנים (`wp:v1:<key>`) לחתונה שנוצרה לו. אין ייבוא שקט:
  על מחשב משותף הנתונים האלה עשויים להיות של אדם אחר. לאחר ייבוא מאושר
  המפתחות הישנים נמחקים.

### עמידות הסנכרון (חשוב)

שתי הגנות שנועדו למנוע **אובדן נתונים שקט** — מצב שבו המשתמש רואה שהכול תקין
אבל השינוי שלו לא נשמר בענן, ובטעינה הבאה הענן דורס אותו:

1. **`last_seen_at` לא נכתב בתוך הטרנזקציה.** הדפדפן שולח כמה בקשות סנכרון
   במקביל (מוזמנים, שולחנות, ספקים, תקציב, הגדרות). כשעדכון השדה התפעולי הזה
   ישב בתוך אותה טרנזקציה `SERIALIZABLE` של קריאת הסשן, כל הבקשות כתבו לאותה
   שורה, CockroachDB החזיר `40001 WriteTooOldError`, הניסיונות החוזרים נגמרו
   והבקשה חזרה 500 — כלומר שמירה אמיתית נכשלה בגלל שדה סטטיסטי. היום העדכון
   יוצא מהטרנזקציה, הוא fire-and-forget, כישלון שלו נבלע, והוא מווסת לפעם
   ב-5 דקות (`TOUCH_EVERY_MS` ב-`server/auth.js`).
2. **ניסיון חוזר אוטומטי.** כישלון סנכרון מתזמן ניסיון נוסף אחרי 5 שניות
   (`scheduleSyncRetry` ב-`src/App.jsx`). הטיימר יחיד בכוונה — כל חמשת
   הסנכרונים חולקים אותו, וניסיון אחד מכסה את כולם.

מדד הסנכרון בכותרת גלוי גם בטלפון (הסמל תמיד, הטקסט רק ממסך `sm` ומעלה),
כדי שלא יהיה מצב שבו עובדים מהנייד בלי שום חיווי אם נשמר.

### עבודה מהנייד (mobile-first)

רוב העבודה על החתונה נעשית מהטלפון, ולכן יש כאן כמה מוסכמות שחשוב לשמור עליהן
כשמוסיפים רכיבים חדשים:

- **44px מינימום לכל דבר שנוגעים בו.** לכפתור או שדה: `min-h-11` ובנוסף
  `sm:min-h-0` כדי שהצפיפות בדסקטופ לא תיפגע. לכפתור אייקון בלבד:
  `grid h-11 w-11 place-items-center` במקום `p-2`. אם 44px שוברים את הפריסה,
  מוסיפים מרווח שלילי (`-m-1.5`) — אזור המגע גדל, המראה נשאר.
- **16px לכל שדה קלט בנייד** (`text-base sm:text-sm`). מתחת ל-16px, ספארי
  ב-iPhone עושה זום אוטומטי בכל פוקוס והמסך "קופץ".
- **תיבות סימון נעטפות ב-`label`** בגודל 44px (`-m-2.5 grid h-11 w-11 ...`).
  תיבה של 16px לבדה כמעט בלתי אפשרית ללחיצה מדויקת באצבע.
- **אין להסתמך על ריחוף.** במסך מגע אין `hover`, ולכן פעולה שמופיעה רק
  ב-`group-hover` פשוט לא קיימת בנייד. משתמשים ב-`opacity-60` קבוע ומעלים
  ל-100% בריחוף/פוקוס.
- **שום דבר לא נחתך.** כפתור פעולה שנשלח ל-`SectionTitle` נעטף ב-
  `w-full min-w-0 sm:w-auto sm:shrink-0`. עם `shrink-0` לבדו טופס שמכיל שדה +
  בורר + כפתור לא יכול היה להתקפל, גלש מחוץ לכרטיס והכפתור נחתך מחוץ למסך.
- **`overflow-x-clip` ולא `overflow-x-hidden`.** שניהם חותכים גלישה אופקית,
  אבל `hidden` הופך את האלמנט למכול גלילה ומשבית כל `sticky` שבתוכו. בתמורה,
  `clip` לא מאפס את רוחב המינימום של פריט `flex`, ולכן `<main>` חייב גם
  `min-w-0` — אחרת מגירת הניווט שמחוץ למסך מוסיפה גלילה אופקית לדף.

### מסך המוזמנים: שני טאבים

עדכון רשימת המוזמנים וסידור ההושבה הן שתי עבודות נפרדות. כשהן היו זו מתחת לזו,
כל כניסה לסידור ההושבה חייבה לגלול דרך מאות שורות (~14,000 פיקסלים ברשימת
הדמו). המסך מפוצל לשני טאבים עם מתג `sticky` בראש התוכן — מעבר ביניהם אפשרי
מכל נקודה ברשימה. כבונוס ביצועים, רשימת המוזמנים לא מרונדרת בכלל כשעובדים על
ההושבה, וגובה הדף יורד ל-~1,200 פיקסלים.

### מה **לא** מיושם, במכוון

**אימות כתובת אימייל.** אין כאן שירות שליחת מיילים, ולכן ההזדהות נעשית
ב**שם משתמש** ולא במייל: השדה משמש רק כמזהה ייחודי להתחברות ולהזמנות שיתוף.
במסד העמודות עדיין נקראות `email` / `email_lower` — לא שונו כדי לא לשבור חשבונות
קיימים. הולידציה יושבת ב-[server/auth.js](server/auth.js) ומפוצלת לשני מפלסים:

- `normalizeUsername()` — בהתחברות ובהזמנות. רק תווים מותרים (`A-Za-z0-9._+@-`) ואורך עד 254.
- `validateNewUsername()` — **בהרשמה בלבד**: 8 תווים לפחות, וחובה אות אנגלית **ו**ספרה.

הפרדה זו מכוונת: החמרת כללים על מסלול ההתחברות היתה נועלת בחוץ חשבונות
שנפתחו לפני שהכללים נכנסו לתוקף. לשינוי שם של חשבון קיים:

```bash
node scripts/rename-user.mjs <שם ישן> <שם חדש>
```

אם ייווסף בעתיד שחזור סיסמה או התראות במייל, יהיה צורך בשדה מייל נפרד
**ובאימות בעלות עליו**.

**הצפנת קצה-לקצה** של טבלאות המוזמנים/התקציב. היא הייתה שוברת סינון
ומיון בצד השרת, הופכת אובדן מפתח לבלתי הפיך, ומגנה מפני תרחיש הרבה
פחות סביר מבעיית ה-RLS הפתוח. הנתונים ממילא מוצפנים בתעבורה (TLS)
ובאחסון (CockroachDB Cloud encryption at rest).

### בדיקת קבלה — הפרדת דיירים

```bash
npm run dev        # בטרמינל אחד
npm run test:api   # בטרמינל שני
```

הבדיקה יוצרת שני משתמשים אמיתיים ועוברת דרך HTTP — בדיוק המסלול של הדפדפן.
לכן היא מוכיחה שה-RLS **אוכף בפועל**, ולא רק שהקוד מתכוון לאכוף.
הריצו אותה רק מול מסד פיתוח. `npm run db:reset -- --yes` מוחק את הסכימה כולה.

בסוף כל ריצה הבדיקה מוחקת את החשבונות שהיא פתחה. אם ריצה נקטעה באמצע
והשאירה שאריות, `npm run test:cleanup` סורק ומוחק כל חשבון שכתובתו מסתיימת
ב-`@test.local`, `@example.test` או `@scope.test` — ורק כאלה.

מה שהבדיקות מכסות (78 טענות):

| נושא | מה נבדק |
| --- | --- |
| הרשמה | שם כפול נדחה; שם קצר/עברי/עם רווח/בלי ספרה/בלי אות נדחה; ההתחברות לא נחסמת בכללי ההרשמה; סיסמה קצרה נדחית; כל משתמש מקבל חתונה משלו |
| בידוד קריאה | B מקבל 0 שורות מהנתונים של A; אנונימי מקבל 401 |
| בידוד כתיבה | `sync` של B לחתונה של A נדחה, והנתונים של A לא משתנים |
| הסלמת הרשאות | B לא רואה את רשימת החברים של A ולא יכול להזמין לחתונה שלו |
| viewer | קורא — אבל כל כתיבה והזמנה נדחות **על ידי מסד הנתונים** |
| הזמנות | טוקן מומצא נדחה; הזמנה נוצלה לא ניתנת למימוש שוב |
| מפתח מורכב | לשתי חתונות יש `id = 1` באותה טבלה, בלי התנגשות |
| הסרת שיתוף | לאחר עזיבה, המשתמש חוזר לחתונה אחת בלבד |
| סשן | התנתקות מבטלת גישה; מייל לא קיים וסיסמה שגויה מחזירים את אותה שגיאה בדיוק |
| שיתוף מסך בודד | הזמנה עם `scopes: ["guests"]` — הנתונים של שאר המסכים לא נקראים ולא נכתבים; עדכון היקף בזמן אמת משנה את מה שנגיש |
| קבצים לספקים | צירוף, רשימה, הורדה ומחיקה — כולם חסומים ללא-חברים; `viewer` לא יכול למחוק |

### שיתוף לפי מסך (scopes)

כל חברות (`wedding_members`) מחזיקה `scopes` — `null` = כל המערכת, או תת-קבוצה
מתוך `["guests", "vendors", "finance"]`. ההיקף נאכף ב-RLS על כל טבלת נתונים,
לא רק בתפריט. הדאשבורד הראשי מוצג רק בשיתוף מלא, כי הוא מסכם את כל המסכים.

### קבצים לספקים

- `GET /api/weddings/:id/files` — רשימת כל הקבצים של החתונה
- `POST /api/weddings/:id/vendors/:vendorId/files` — צירוף קובץ
- `GET /api/weddings/:id/files/:fileId` — הורדה/צפייה
- `DELETE /api/weddings/:id/files/:fileId` — מחיקה

מגבלת גודל: **5MB** לקובץ. רק סוגי MIME בטוחים מוצגים inline בדפדפן
(SVG **לא** ברשימה — הוא יכול להריץ JavaScript); כל השאר יורדים כקובץ.

### שליחת הזמנת שיתוף

השרת **לא** שולח מיילים. לאחר יצירת ההזמנה מוצג הקישור עם שלוש דרכי שליחה:
ווטסאפ (`https://wa.me/?text=`), אימייל (`mailto:`) והעתקה ידנית. שתי הראשונות
נפתחות עם `noopener,noreferrer` — הקישור מכיל את טוקן ההזמנה, ואסור לתת לדף
היעד גישה לחלון שלנו.

### ייצוא לאקסל

התפריט של כפתור **גיבוי** מציע שתי פעולות: קובץ JSON לשחזור, וקובץ XLSX
לקריאה. הייצוא מיושם ב-[src/lib/excelExport.js](src/lib/excelExport.js) ומחולק
לארבעה גיליונות: **מוזמנים** (14 עמודות, כולל השולחן שאליו שובץ כל אחד),
**ספקים** (כולל תקציב, יתרה, הערות ופירוט כל המשימות — בלי הקבצים המצורפים),
**סדר הושבה** (שורה לכל צירוף שולחן-מוזמן, כולל שולחנות ריקים ומי שלא שובץ)
ו**ניהול תקציב** (כולל שורות סיכום והכנסות ממתנות).

`buildSheets` היא פונקציה טהורה בלי DOM, ו-ExcelJS נטען ב-import דינמי כדי
שלא ייכנס ל-bundle הראשי. אימות: `npm run test:excel` (44 טענות) בונה חוברת,
קורא אותה בחזרה ומשווה כל תא לנתוני המקור.

### שמות בני הזוג — מקור אמת יחיד

השמות שמוזנים בכותרת הדאשבורד הם המקור היחיד לשם שמוצג בסרגל הצד, במחליף
החתונות, בפורטל הספקים, בהודעת ההזמנה ובשם קובץ האקסל. הם נשמרים בעמודות
`partner_a` / `partner_b` על `public.weddings` — ולא ב-localStorage — כדי שהם
יסונכרנו בין מכשירים וייראו גם למי שהחתונה שותפה איתו. עריכה מותרת לבעלים
בלבד, כפי שה-RLS מתיר.

עמודת `name` של החתונה נשארת כגיבוי בלבד, לחתונה שעדיין לא מילאו בה שמות
(`weddingLabel()` ב-[src/App.jsx](src/App.jsx) הוא הפונקציה שקובעת את הסדר).
`PATCH /weddings/:id` מעדכן רק את השדות שנשלחו בפועל, כך שעדכון השמות לא
מוחק את התאריך ולהפך.

### הגדרות החתונה

יעד התקציב, קטגוריות המוזמנים וכותרות מסך התקציב נשמרים בטבלה
`public.wedding_settings` (עמודת `data` מסוג JSONB), ולא ב-localStorage — כך
הם שורדים יציאה מהמערכת ומופיעים גם במכשיר אחר ואצל מי שהחתונה שותפה איתו.

זו טבלה נפרדת ולא עמודה על `public.weddings` בכוונה: מדיניות ה-UPDATE על
`weddings` פתוחה לבעלים בלבד (שם, תאריך, שמות בני הזוג), בעוד שהקטגוריות ויעד
התקציב הם נתון שיתופי שכל מי שיש לו הרשאת עריכה אמור לשנות. טבלה נפרדת מקבלת
מדיניות `can_edit_wedding` משלה בלי להחליש את ההגנה על `weddings`. אין הרשאת
DELETE, גם לא לבעלים.

* קריאה: ההגדרות חוזרות בתוך `GET /weddings/:id/data`, כדי שטעינת המסך תישאר
  בקשה אחת. הן מסוננות לפי היקף השיתוף — מי ששותף איתו מסך המוזמנים בלבד לא
  מקבל את יעד התקציב.
* כתיבה: `PUT /weddings/:id/settings` היא **כתיבת מיזוג** ולא החלפה
  (`data || excluded.data`). זה קריטי: בלי זה, שמירת קטגוריות בידי עורך
  שמשותף איתו רק מסך המוזמנים הייתה מוחקת את יעד התקציב שהוא אינו רואה.
* מפתח שאינו ברשימה הלבנה נזרק, ויש תקרות גודל לכל שדה.

כל ההגדרות הקבועות — שמות בני הזוג, תאריך החתונה ויעד התקציב — נמצאות במקום
אחד: "הגדרות החתונה" בסרגל הצד. אלה נתונים שנקבעים פעם אחת, ולכן הם אינם
מופיעים בתוך מסכי העבודה.

### התחברות ואיפוס סיסמה

המזהה של המשתמש הוא **כתובת מייל** (מנורמלת ל-lowercase ב-`normalizeEmail`).
זו אינה החלטה קוסמטית: המייל הוא הערוץ היחיד להחזרת גישה למי ששכח סיסמה,
ולכן מזהה שאינו כתובת אמיתית היה נועל משתמשים בחוץ לצמיתות.

מסך ההרשמה מבקש שלושה שדות בלבד — מייל, תאריך חתונה (אופציונלי) וסיסמה.
התאריך נבדק בשרת ב-`normalizeDate`, שדוחה גם `2028-02-31` (רגקס לבדו מקבל
תאריך כזה; ההשוואה חזרה למחרוזת אחרי `Date` היא מה שפוסל אותו).

זרימת האיפוס:

1. `POST /api/auth/forgot` — **תמיד** מחזיר `200 {ok:true}`, גם לכתובת שאינה
   רשומה. תשובה שונה הייתה הופכת את הטופס לכלי לגילוי מי רשום במערכת.
2. נוצר טוקן אקראי (32 בתים). ב-`app.password_resets` נשמר **רק ה-hash** שלו,
   בדיוק כמו בסשנים. הטבלה יושבת בסכמה `app` שאין לה GRANT ל-`app_user`,
   ולכן גם באג ב-RLS של נתוני החתונה לא יכול להגיע לטוקני איפוס.
3. הקישור נשלח במייל ותקף שעה אחת.
4. `POST /api/auth/reset` ממש את הטוקן ב-`UPDATE ... WHERE used_at IS NULL AND
   expires_at > now()` יחיד — כך המימוש אטומי וטוקן לא ניתן לשימוש פעמיים גם
   בשתי בקשות מקבילות.
5. אחרי איפוס **כל הסשנים של המשתמש נמחקים**. בלי זה, מי שכבר היה מחובר
   לחשבון נשאר מחובר, וכל התועלת שבאיפוס מתבטלת.

בצד הלקוח הטוקן נקרא מ-`?reset=` ונמחק מיד משורת הכתובת. בניגוד לטוקן הזמנה
הוא **אינו** נשמר ב-sessionStorage — טוקן שמאפשר לקבוע סיסמה לא צריך לשרוד
רענון דף.

הגבלת הקצב סופרת ניסיונות ניחוש בלבד (401), ולא 400 על קלט פסול; נתיבי
`forgot`/`reset` נספרים בכל מקרה כי שם *כל* פנייה היא ניסיון.

#### שליחת מייל — משתני סביבה

בלי SMTP מוגדר המערכת עובדת, אך קישור האיפוס **מודפס ללוג השרת** במקום
להישלח. להפעלה אמיתית הוסיפו ל-`.env`:

```
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_USER=you@gmail.com
SMTP_PASS=<App Password, לא סיסמת החשבון>
SMTP_FROM="תכנון החתונה שלנו <you@gmail.com>"
APP_URL=http://localhost:5173
```

ב-Gmail חובה אימות דו-שלבי ו-App Password ייעודי. `sendPasswordResetEmail`
לעולם אינו זורק — כשל בשליחה לא אמור להפיל בקשת התחברות.
